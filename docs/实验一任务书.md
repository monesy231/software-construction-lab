# 《软件构造实践》实验一任务书

- **项目名称**：基于 Android 的飞机大战游戏迁移与网络功能扩展
- **Android 工程名称**：`AircraftWar2026`
- **组队形式**：单人组

---

## 一、项目概述

### 1.1 项目内容
本项目将《软件构造》课程中基于 Java 与 Swing 开发的 Windows 桌面版《飞机大战》程序（`WindowsAircraftWar`）迁移至 Android 移动平台（`AircraftWar2026`），并在保留原有经典玩法（三种难度模式、五种敌机、多种弹道射击策略、五种道具效果、本地得分排行榜）与面向对象设计模式的基础上，进一步扩展移动触屏交互、Android 多界面跳转、音频系统以及两项联网对战与排行榜功能。

### 1.2 实施意义
1. **掌握跨平台迁移方法**：通过拆分“平台无关的核心业务逻辑”与“平台相关的图像加载、渲染循环、触屏输入、界面和音频层”，深入理解分层架构与接口隔离在跨平台软件工程中的实际价值。
2. **巩固面向对象设计模式**：在实际工程中继续沿用并验证单例模式、简单工厂、工厂方法、策略模式、观察者模式、模板方法模式及 DAO 模式在不同运行环境下的可移植性与复用性。
3. **建立 Android 工程开发能力**：通过完成 `Activity` 生命周期管理、`SurfaceView` 双缓冲子线程绘制、`Handler` 线程间通信、Android 内部文件存储及网络异步编程，形成完整的 Android 应用开发闭环能力。

## 二、原有功能迁移分析

### 2.1 待迁移代码来源
本项目选择迁移本组成员项目成员在 Windows 平台完成的 Java 源码工程 `WindowsAircraftWar`（共 53 个 Java 类及配套图片、音频资源），同时参考课程提供的 `SurfaceViewDemo` 示例工程实现 Android `SurfaceView` 绘制框架。

### 2.2 可复用模块及原因

| 模块 | 包含主要类 | 复用方式 | 可复用原因 |
| :--- | :--- | :--- | :--- |
| **飞机与子弹实体** | `AbstractAircraft`、`AbstractEnemy`、`MobEnemy`、`EliteEnemy`、`ElitePlusEnemy`、`EliteProEnemy`、`BossEnemy`、`BaseBullet`、`HeroBullet`、`EnemyBullet` | 直接复制保留 | 属性维护、血量增减、碰撞矩形判定与移动逻辑均为纯 Java 计算，不依赖桌面 GUI 库。 |
| **道具与观察者** | `AbstractSupply`、`BloodSupply`、`BombSupply`、`FireSupply`、`FirePlusSupply`、`FreezeSupply`、`PropObserver`、`PropSubject`、`BombPropSubject`、`FreezePropSubject`、`FirePowerRunnable` | 直接复制保留 | 道具掉落、炸弹清屏通知、冰冻定身通知及火力恢复计时线程仅依赖标准 Java 接口与线程库，与平台无关。 |
| **敌机与道具工厂** | `EnemyFactory` 及其 5 个子类、`SupplyFactory`、`SupplyType` | 直接复制保留 | 工厂方法与简单工厂通过 `ImageManager` 获取图片宽高；Android 的 `Bitmap` 与原 `BufferedImage` 同样具备 `getWidth()`/`getHeight()` 方法，调用接口完全兼容。 |
| **射击策略** | `ShootStrategy`、`NoShootStrategy`、`StraightShootStrategy`、`DoubleStraightShootStrategy`、`ScatterShootStrategy`、`CircleShootStrategy` | 直接复制保留 | 不同弹道的坐标偏移与速度矢量计算纯属数值运算，与界面显示层完全解耦。 |
| **难度模板** | `GameDifficulty`、`EasyGame`、`NormalGame`、`HardGame` | 保留逻辑（子类构造传入 `Context`） | 简单、普通、困难三种难度的敌机概率、生成周期、Boss 触发阈值与难度递增规则无需改变。 |
| **排行榜模型与 DAO** | `ScoreRecord`、`ScoreBoardService`、`ScoreDao`、`ScoreDaoImpl` | 实验四复用 | 文本记录序列化、排序与按名次删除规则不依赖桌面界面；只需在 Android 端将文件目录替换为 `Context.getFilesDir().toPath()` 即可复用。 |

### 2.3 需重新适配 Android 平台的功能模块及原因

| 模块 | Windows 端实现 | Android 端适配方案 | 需要适配的原因 |
| :--- | :--- | :--- | :--- |
| **图形基础类型与英雄机初始化** | `AbstractFlyingObject` 使用 `BufferedImage` 且连续冻结、边界冻结及减速期增速存在速度失真；`HeroAircraft` 使用饿汉式单例 | `AbstractFlyingObject` 将 `BufferedImage` 替换为 `android.graphics.Bitmap`，采用 `baseSpeedX/Y`、`effectRate`、`getBaseSpeedY()` 与版本令牌修复连续/边界冻结及减速期叠加增速问题；`HeroAircraft` 改为懒汉式单例，并在 `resetState()` 中递增 `fireVersion` | Android SDK 不包含 `java.awt.image.BufferedImage`；同时避免类加载早于图片解码引发空指针，并消除跨局火力恢复及冻结/减速速度恢复异常。 |
| **图片资源加载** | `ImageManager` 通过 `ImageIO.read` 读取文件路径 | 图片放入 `res/drawable/`（重命名为全小写下划线格式），改用 `BitmapFactory.decodeResource` 加载 | Android 通过资源 ID（`R.drawable.*`）管理打包图片，且不支持 `javax.imageio.ImageIO`。 |
| **游戏入口与双生命周期** | `Main` 使用 `JFrame`、`CardLayout`；`Game` 继承 `JPanel`，使用 `java.util.Timer` 和 `paint(Graphics)` | `Main` 保留可变屏幕尺寸常量；`MainActivity` 在 `onResume`/`onPause` 驱动游戏启停；`Game` 重构为 `SurfaceView`，由 `Activity` 生命周期与 `SurfaceHolder.Callback` 共同控制单 `GameThread` 并使用 `Canvas` 绘制 | Android 中 `Activity`（锁屏触发 `onPause` 但未必销毁 Surface）与 `Surface` 生命周期相互独立，必须双门控管理线程，避免锁屏后台继续运行或阻塞主线程导致 ANR。 |
| **屏幕分辨率适配** | 固定窗口尺寸 `512×768` | 在 `SurfaceHolder.Callback.surfaceChanged` 中获取真实宽高更新 `Main.WINDOW_WIDTH/HEIGHT`、缩放背景图；尺寸变化时按比例换算英雄机位置并按半宽半高夹紧 | Android 设备屏幕尺寸多样且可能发生窗口尺寸变化，必须动态同步画布尺寸、背景缩放与精灵可见边界。 |
| **玩家输入交互** | `HeroController` 使用 `MouseAdapter.mouseDragged` 监听鼠标拖拽 | 改用 `game.setOnTouchListener` 监听 `ACTION_DOWN` 与 `ACTION_MOVE`，按英雄机半宽半高对中心坐标进行屏幕边界夹紧 | 移动端通过触屏控制，且精灵位置为图片中心点，必须夹紧到 `[halfW, WINDOW_WIDTH - halfW]` 范围内防止拖动到边缘被裁切。 |
| **页面切换与音频（实验三）** | Swing `StartMenu` / `ScoreBoardFrame`；`javax.sound.sampled` 播放 `.wav` | 改用 `StartMenuActivity`、`ScoreBoardActivity`、`Intent` 与 `Handler`；音频放 `res/raw/`，改用 `MediaPlayer` + `SoundPool` | Android 不支持 Swing 组件及 `javax.sound.sampled` 音频库，且子线程结束游戏后必须切回主线程更新 UI。 |

## 三、新增网络功能设计

计划在实验五中至少实现以下两项网络功能：

### 3.1 网络功能一：云端全服排行榜同步
- **功能内容**：玩家在单局游戏结束后，可选择将本局成绩（玩家昵称、得分、难度模式、记录时间）上传至云端服务器；在排行榜界面支持切换查看“本地排行榜”与“云端全服排行榜”。
- **设计原因**：单机版排行榜仅保存在本地设备中，无法与其他玩家对比成绩；新增云端排行榜能够自然衔接实验四的本地 DAO 排行榜模块，提升游戏竞技性。
- **技术实现思路**：
  1. 服务端使用轻量级 HTTP 接口（如 `POST /scores` 提交成绩、`GET /scores?difficulty=easy` 查询前 N 名记录）及 JSON 数据格式存储与排序全服成绩。
  2. 客户端在 `AndroidManifest.xml` 中声明 `INTERNET` 权限，在子线程中使用 `HttpURLConnection` 发起异步上传与拉取请求。
  3. 网络请求完成后通过 `Handler` / `runOnUiThread` 将解析后的 `ScoreRecord` 列表回调至主线程刷新排行榜界面。

### 3.2 网络功能二：双人实时得分对战模式
- **功能内容**：两名玩家分别在各自设备上登录/进入同一对战房间并选择相同难度同步开局；对局过程中界面实时显示对手当前得分与生命状态（存活或阵亡），双方游戏均结束后比对最终得分并判定胜负。
- **设计原因**：相比实时同步全屏上百个子弹与敌机坐标，“双人状态与得分同步”的数据报文极小、对网络抖动不敏感，既能带来双人对战的紧张感，又能保证单局帧率流畅稳定。
- **技术实现思路**：
  1. 基于 TCP `Socket` 搭建房间匹配与消息转发服务（服务端负责房间配对、同步发送开局信号与转发双方状态消息）。
  2. 客户端开局后启动独立网络收发子线程，游戏循环每约 500ms 发送一次自身状态帧（玩家标识、当前分数、剩余生命、是否结束），并接收对手最新状态存入字段。
  3. 游戏绘制线程在 `Canvas` 右上角实时绘制对手分数与状态，游戏结束等待对手结算或接收对手终局分数后弹出胜负结果界面。
